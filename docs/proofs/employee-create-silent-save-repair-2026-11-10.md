# EMPLOYEE CREATE SILENT-SAVE DEFECT REPORT

Date: **2026-11-10, Asia/Aden**. Repair status: **COMPLETE**, with the observation limits below. Final decision: **EMPLOYEE_CREATE_SAVE_FIXED**.

The repair is built and deployed to the existing local API and Web services. The owner confirmed after deployment: **«ظهرت رسائل التحقق بوضوح»** when saving the empty Create form. No real employee or test account was created in Production by this task.

## Root Cause

The real page and its real `useCrudList` hook reproduced a silent failure using an actual HTTP 400 response captured from the unchanged compiled API in a fresh disposable SQL Server clone. `onError` first stored a form-level message. The subsequent `onFieldErrors` replaced that entire error map, removing the summary. Backend paths such as `password`, `login.email`, and `placement.departmentId` did not match flat controls such as `loginPassword`, `loginEmail`, and `departmentId`. A rejected request could therefore finish with `saving=false`, the modal open, and no rendered error, toast, or error dialog. Missing stable control IDs also made focus fall back to the first input, including the optional code field.

This proves the error-display defect and a concrete failing Save path. The original user's password was not inspected, and the precise error from the original historical click was not captured. It would be incorrect to assert that the original password definitely violated policy. Empty login fields and other nested validation errors are covered by the same repaired feedback path.

Additional create-contract gaps found during the audit: department and password requiredness were not sufficiently visible; the initial branch was not derived from active context; missing placement and blank/whitespace name were insufficiently constrained at DTO level; locale-dependent dates could pass a permissive service parser. These were corrected within the registration flow.
