## 2. الإضافة (Create) vs التعديل (Update)

### ✅ آلية التمييز بين الإضافة والتعديل

**على مستوى API (Backend):**
```
إنشاء (POST)   → /api/v1/endpoint         → ينشئ سجل جديد + يولد رقم تلقائي
تعديل (PATCH)  → /api/v1/endpoint/:id     → يحدث السجل الموجود (نفس الـ id)
حذف (DELETE)   → /api/v1/endpoint/:id     → Soft delete
```

**على مستوى الواجهة (Frontend) — 3 أنماط:**

| النمط | الأمثلة | آلية التمييز |
|-------|---------|-------------|
| Modal عبر `useCrudList` | companies, departments, branches | `editItem == null` → Create / `editItem != null` → Edit |
| Modal يدوي | warehouses, spare-parts, checklist-items | `editingId == null` → POST / `editingId != null` → PATCH |
| صفحات منفصلة | `warehouses/new/` vs `warehouses/[id]/edit/` | المسار يحدد: new = POST, edit = PATCH |

### ✅ اختبار عملي — ناجح 100%

```
1. إنشاء تصنيف منتج: ✅ POST → 201, id=new, code=AutoGenerated
2. تعديل التصنيف:     ✅ PATCH/:id → 200, same id, same code, name changed
3. التحقق من التعديل: ✅ نفس السجل (id و code لم يتغيرا) — لم يتم إنشاء سجل جديد
4. الحقول غير المرسلة: ✅ description بقي كما هو (Partial Update)
```

### ✅ فحص وجود السجل قبل التعديل
- كل `service.update()` يستدعي `findOne(id)` أولاً
- إذا كان id غير موجود → `NotFoundException` (404)

### ✅ منع تغيير الكود بعد الإنشاء
- `SparePartsService.update()`: يمنع تغيير الحقل `code` بعد الإنشاء
- `BadRequestException('Code cannot be changed after creation')`

## 3. التعامل مع الأخطاء

### ✅ نظام الأخطاء متعدد المستويات

| المستوى | المكون | الموقع | الاستخدام |
|---------|--------|--------|-----------|
| **1** | Toast (إشعار منبثق) | `toast-provider.tsx` | ✅ يستخدم في 100+ صفحة |
| **2** | ErrorState (حالة خطأ) | `error-state.tsx` | ✅ يستخدم في 100+ صفحة |
| **3** | Error Modal (نافذة خطأ) | `error-modal.tsx` | ⚠️ معرف ولكن **غير مفعل** |
| **4** | AlertBanner (شريط تنبيه) | `alert-banner.tsx` | ⚠️ معرف ولكن غير مستخدم |
| **5** | Global Exception Filter | `http-exception.filter.ts` | ✅ يمسك كل الأخطاء ويحولها لـ JSON |

### ✅ كيف يظهر الخطأ للمستخدم؟

**حالة 1: خطأ أثناء الحفظ/الإضافة/التعديل**
```
→ Toast أحمر في أعلى اليمين لمدة 4 ثواني
→ فيه زر X للإغلاق اليدوي
→ الرسالة واضحة وتشرح السبب
```

**حالة 2: خطأ أثناء تحميل البيانات**
```
← ErrorState في منتصف الصفحة: نص أحمر + زر إعادة المحاولة
← ما يختفي لحين النقر على إعادة المحاولة
```

**حالة 3: أخطاء API من الباك اند**
```
→ جميع الأخطاء تعود بهيكل موحد:
  {
    "success": false,
    "statusCode": 4xx,
    "message": ["رسالة واضحة بالعربية أو الإنجليزية"],
    "messageKey": "error.code",
    "timestamp": "..."
  }
```

### ✅ اختبار الأخطاء العملي

| السيناريو | النتيجة |
|-----------|---------|
| إنشاء بكود مكرر | ✅ HTTP 409: "Category code already exists" |
| إنشاء بحقل إجباري ناقص | ✅ HTTP 400: "code must be a string" |
| تعديل بسجل غير موجود | ✅ HTTP 404: NotFoundException |
| صرف من مخزن خاطئ | ✅ HTTP 400: "Spare parts cannot be issued from product warehouses" |
| صرف بكمية أكبر من الرصيد | ✅ HTTP 400: "Insufficient condition balance... Available: 0, Requested: 1" |
| أخطاء الـ Validation العامة | ✅ HTTP 400 مع تفاصيل الأخطاء |

### ⚠️ ملاحظات على الأخطاء

**إيجابي:**
- نظام API i18n موجود بـ 110+ مفتاح (عربي + إنجليزي)
- الـ Global Exception Filter يدعم اللغة تلقائياً
- `getRequestLanguage()` يستخرج اللغة من `x-locale` ← `Accept-Language` ← fallback AR

**تحتاج تحسين:**
- `error-modal.tsx` غير مفعل — يمكن استخدامه للأخطاء الحرجة (نافذة في منتصف الصفحة)

## 4. الفرق بين قطع الغيار والمنتجات

### ✅ الفصل التام على مستوى API

| الكيان | الـ Endpoint | حقول البحث | الأماكن |
|--------|-------------|-------------|---------|
| **قطع غيار (Spare Parts)** | `/maintenance/spare-parts` | code, name, partNumber | صيانة فقط |
| **منتجات (Products)** | `/products` | code, name, barcode | مخازن فقط |

### ✅ اختيار القطعة في F9
```
F9Adapter للمنتجات:    endpoint = /products           → يستخدم في المخازن
F9Adapter لقطع الغيار: endpoint = /maintenance/spare-parts → يستخدم في الصيانة
```

### ✅ منع استخدام مخازن المنتجات في الصيانة

**في `MaintenanceStockIssueService`:**
```typescript
const FORBIDDEN_WAREHOUSE_TYPES = ['PRODUCT', 'RAW_MATERIAL'];
// إذا حاول المستخدم الصرف من مخزن PRODUCT → BadRequestException
```

**في `RepairOrdersService`:**
```typescript
if (warehouseType !== 'SPARE_PART') {
  throw new BadRequestException('Spare part warehouse required');
}
// فقط SPARE_PART مسموح
```

### ✅ لا يوجد تداخل في المعرفات
- اختبار: 0 منتجات تشترك في id مع قطع الغيار (id's مختلفة تماماً)
- كل spare part يرتبط بـ product عبر `productId` (في الخلفية فقط)

### ⚠️ ملاحظة: أنواع المخازن
- المخازن الحالية في قاعدة البيانات ليس لها نوع (`warehouseType` = فارغ)
- هذا يعني أن التحقق `FORBIDDEN_WAREHOUSE_TYPES` لن يمنع المخازن الحالية
- يجب تحديث المخازن بأنواعها الصحيحة (SPARE_PART, PRODUCT, RAW_MATERIAL, GENERAL)
