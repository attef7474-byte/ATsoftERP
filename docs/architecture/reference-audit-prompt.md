# برومبت التدقيق المرجعي — ATsoft ERP Reference Audit Prompt

**الإصدار:** 1.0  
**الغرض:** قالب موحد لتدقيق أي ميزة أو إصلاح أو وحدة في ATsofterp بعد اكتمال التنفيذ. يُستخدم للتحقق المستقل من أن التغيير يلتزم بالدستور ويشغّل مساراً حقيقياً.

---

## 1. الغرض

نفّذ تدقيقاً مستقلاً للميزة/الوحدة التالية في مستودع `ATsofterp`:

> **[أدخل الميزة/الوحدة/نقطة النهاية/الصفحة محل التدقيق]**

الهدف: التحقق من أن التنفيذ **حقيقي ومتصل ومحفوظ**، وليس مجرد كود يترجم بنجاح.

## 2. التحقق من الحالة الأساسية

1. سجّل الفرع والالتزام والملفات المعدلة وغير المتعقبة قبل أي فحص.
2. اقرأ الدستور: `docs/architecture/atsoft-erp-engineering-constitution-v1.0.md`.
3. حدد ملفات التنفيذ ذات الصلة من تقرير الإثبات إن وُجد، أو من الـ git log.

## 3. قائمة الفحص (تحقق فعلي — لا افتراضات)

### أ. الواقع التشغيلي
- هل يوجد مسار حقيقي: `Frontend → API → Permission → Service → Database → Audit → Result`؟
- هل النموذج يُحفظ عبر API حقيقي؟
- هل الأزرار لها معالجات حقيقية؟
- هل توجد بيانات مزيفة أو صفحات وهمية أو استجابات ثابتة؟

### ب. عزل المستأجر والفرع
- هل الشركة/الفرع مفرضان في الـ backend؟
- هل يمكن للشركة B قراءة أو تحرير سجل الشركة A بالـ id؟
- هل يمكن الإشارة لسجل عبر الشركات في معاملة جديدة؟
- هل البحث والتصدير نطاقهما الشركة/الفرع؟
- هل يُستخدم SUPER_ADMIN لإخفاء غياب الفرض؟

### ج. الصلاحيات
- هل الصلاحية معرّفة ومُبذورة؟
- هل فُرِضت في الـ backend؟
- هل استُخدمت في الـ frontend؟
- هل اختُبرت للأدوار المسموحة والمرفوضة؟

### د. التدقيق
- هل أُدرج الإجراء الحساس بالكيان والوقت والقيم والمستخدم؟
- هل السبب مطلوب عند الحاجة؟

### هـ. البيانات والحساب
- هل المعاملة الذرية مسجلة مرة واحدة بكل الأبعاد؟
- هل تُجمع الإجماليات من السجلات الذرية دون ازدواج؟
- هل استخدم `Decimal` للنقود والكميات؟
- هل منع رصيد المخزون السالب؟

### و. الترجمة والاتجاه
- هل دعمت العربية والإنجليزية؟
- هل مفاتيح الترجمة متزامنة؟
- هل لا توجد مفاتيح خام للمستخدم؟
- هل اختُبرت RTL وLTR؟

### ز. الاختبارات
- هل الاختبارات ذات معنى وتمر؟
- هل يوجد اختبار عزل مستأجر؟
- هل الاختبارات المرتبطة مكتوبة فعلاً (لا فارغة/مخطّية)؟

### ح. سلامة الترحيل والبيانات
- هل الترحيحات مراجَعة وآمنة (nullable → backfill → constraints)؟
- هل حُفظت البيانات القائمة؟
- هل لا يوجد تحرير لترحيح مطبق أو إعادة تعيين مدمرة؟

### ط. الأداء والأمان
- هل توجد استعلامات قوائم غير محدودة أو N+1؟
- هل تُكشف الأسرار أو بيانات اعتماد الإنتاج؟

## 4. أدوات التحقق (استخدم حسب الحاجة)

- `npx prisma validate` و`npx prisma generate`.
- فحص أنواع الـ backend (`tsc --noEmit`).
- فحص أنواع/بناء الـ web.
- اختبارات مركزة (`npx jest <spec>` أو أمر المشروع).
- فحص i18n (تزامن المفاتيح).
- إثبات متصفح/API حقيقي للسير الحرجة.
- `git diff --check`.

## 5. تقرير التدقيق

أعد تقريراً بالمواضيع التالية:

1. **الخلاصة:** `PASS` / `PASS WITH NOTES` / `FAIL`.
2. **الحقائق المثبتة** (مع الأدلة والمسارات).
3. **قائمة فحص التفصيل** (كل بند: مُثبت / غير مُثبت / غير مطبق).
4. **الملاحظات** (غير حرجة لكن جديرة بالمراجعة).
5. **التجاوزات الحرجة** (إن وُجدت): فقدان بيانات، كشف عبر الشركات، ترحيل مدمر، حسابات خاطئة، سير عمل غير قابل للتراجع.
6. **التوصيات** المرتبة بالأولوية.
7. **حالة Git** بعد التدقيق (يجب ألا يغيّر التدقيق الملفات).

لا تُصدِر أحكام "سليمة" دون أدلة. كل بند يجب أن يشير إلى ملف/سطر/أمر/لقطة فحص.
