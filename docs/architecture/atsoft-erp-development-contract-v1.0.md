# عقد تطوير ATsoft ERP الدائم — ATsoft ERP Permanent Development Contract

**الإصدار:** 1.0
**تاريخ الإصدار:** 2026-08-02
**الحالة:** موثق — العقد التنفيذي الدائم لأي مهمة في ATsofterp، في أي أداة وفي أي جلسة.

---

## 0. سلطة المرجع والاستخدام

1. هذا العقد يُقرأ كاملاً عند بدء **كل** جلسة تنفيذ جديدة، ثم يُفتح القالب الزمني (القسم 17) ويُملأ بالمهمة.
2. الترتيب المرجعي عند التعارض:
   1. الدستور الهندسي `docs/architecture/atsoft-erp-engineering-constitution-v1.0.md`.
   2. ملفات قواعد النطاق في `docs/agent-rules/` (المعنية فقط بالمهمة).
   3. هذا العقد.
   4. `AGENTS.md` (ملخص تشغيلي).
   5. تقارير الاكتشاف في `docs/proofs/` (أدلة، وليست سلطة تصميم).
3. هذا العقد صالح لأي أداة ذكاء اصطناعي أو مهندس؛ يُنسخ كاملاً أو يُضاف كبرومبت نظام ثابت، ويُحفظ في المستودع ليقرأه الجميع.
4. المهمة لا تبدأ قبل قراءة العقد والدستور وتسجيل حالة المستودع.

---

## 1. القواعد الثابتة للمشروع — Permanent Project Rules

1. **الواقعية الإلزامية:** لا بيانات مزيفة، ولا صفحات/أزرار وهمية، ولا استجابات نجاح ثابتة، ولا أشكال لا تُحفظ عبر API حقيقي، ولا واجهات معزولة عن قاعدة البيانات، ولا كتل `catch` تخفي أخطاء، ولا تعطيل تحقق لتمرير بناء. الميزة مكتملة فقط عندما يكون مسارها `قاعدة بيانات → API → صلاحية → خدمة → واجهة → ترجمة → اختبارات → إثبات` متصلاً.
2. **الحفاظ على ما يعمل:** الكود الحالي هو المصدر النهائي للحقيقة. لا تُعَد وحدات تعمل دون ترحيل معتمد.
3. **لا نطاقات غير معتمدة:** لا تفتح Finance/Sales/Purchasing/HR payroll/AI/IoT/BI/تنبؤ أو أي نطاق غير معتمد دون طلب صريح (المادة 28 من الدستور).
4. **حفظ البيانات:** لا `prisma migrate reset`، ولا حذف جداول، ولا `db push` غير مراجع، ولا تحرير ترحيحات مطبقة، ولا إنشاء قاعدة بيانات من جديد لحل مشكلة schema.
5. **الأمان:** لا أسرار في الكود أو الالتزامات (سلسلة اتصال، JWT، مفاتيح API، كلمات مرور). لا عمليات Git كتابية دون طلب صريح.

---

## 2. قواعد البنية — Architecture Rules

1. **منع التكرار (إلزامي):** قبل إنشاء أي صفحة أو API أو نموذج أو مكون أو خدمة أو مفتاح ترجمة، ابحث عن الموجود أولاً: `grep`/`glob` عبر `apps/api/src` و`apps/web/src` ومفاتيح i18n، ثم ابنِ على الموجود أو عدّله. لا نُبني نسخة موازية لمفهوم قائم. أي تكرار مُكتشف يُحذف أو يُدمج.
2. **الشريحة الرأسية (Vertical Slice):** كل ميزة تُنفذ كشريحة كاملة: ترحيل آمن → DTOs → خدمة → تحكم → صلاحيات → تدقيق → صفحات → ترجمات AR/EN → اختبارات → إثبات تشغيلي. لا توجد شريحة "backend فقط" أو "frontend فقط" تُعلن مكتملة.
3. **الوحدات النظيفة:** التحكم رقيق (thin controller)، الخدمة تحتوي منطق الأعمال، التحقق لا يُثق بالواجهة.
4. **أنماط موحدة:** نفس أنماط الترقيم (POST إنشاء + `PATCH /:id` تحديث)، والترقيم التلقائي، والسياق التشغيلي النشط، ونفس بنية الاستجابة الموحدة وأكواد الخطأ.
5. **أصغر تنفيذ آمن:** عند غموض النطاق استخدم أصغر تنفيذ يحقق النتيجة كاملة دون تكرار أو تجاوز.

---

## 3. قواعد قاعدة البيانات — Database Rules

1. **Prisma فقط** هو أداة الوصول؛ لا SQL خام في الخدمات إلا عبر Prisma `$queryRaw` الموثق والمراجع.
2. **الترحيلات الآمنة:** كل تغيير schema بترحيل جديد مراجع. الحساس منها متدرج: بنية nullable → backfill → تحقق → قيود → سلوك التطبيق → إهمال في مهمة منفصلة. لا تعديل لترحيح مطبق أو حذف سجل الترحيلات.
3. **القيود:** `Decimal(18,2)` للنقود والكميات الدقيقة؛ `@@unique` و`@@index` للنطاقات الواقعية؛ مفاتيح أجنبية مع `onDelete: NoAction` للحماية من الحذف المتسلسل غير المقصود.
4. **الذرّية:** العمليات متعددة السجلات (مخزون، تركيب/استبدال، إنتاج، انتقالات حالة) داخل `$transaction`. لا تعديل رصيد مخزون دون معاملة مصدر مصرح بها. لا سجل تجاري واحد يُخزن كحقيقة مكررة في مستويات متعددة؛ سجّل الحدث الذري مرة واحدة بكل الأبعاد، ثم اجمع في التقارير.
5. **الفهارس:** فقط لمسارات استعلام حقيقية مع فهم أثر الكتابة/التخزين.

---

## 4. قواعد المستأجر — Tenant Rules

1. **الشركة والفرع هما حد أمني إلزامي** في كل عملية: إنشاء/قراءة/تحديث/حذف/بحث/تصدير/طباعة/مرفقات/إشعارات/تدقيق/خلفية.
2. يُفرض نطاق الشركة/الفرع في **backend** حصراً. لا يُثق أبداً بـ header أو حقل مخفي من الواجهة. لا تُجلب سجلات مملوكة بـ `id` وحده دون نطاق.
3. **التحقق من المصداقية:** كل مرجع (آلة، مخزن، منتج، مستخدم، أمر...) يُتحقق من انتمائه لنفس سياق الشركة/الفرع قبل استخدامه. منع العلاقات عبر الشركات والفرع غير المصرح.
4. **السياق النشط:** قراءة `x-active-company-id` و`x-active-branch-id` فقط من جلسة تسجيل الدخول المعتمدة. غياب السياق = رفض (403)، وليس توسيعاً صامتاً للوصول.
5. **SUPER_ADMIN:** سلوكه صريح ومُدقق؛ لا يُستخدم لإخفاء غياب فرض المستأجر للأدوار العادية.
6. **اختبارات العزل:** شركة A تقرأ سجلها؛ شركة B تُرفض قراءته/تعديله بالـ id؛ شركة B لا تشير إليه في معاملة جديدة؛ وصول فرع غير مصرح يُرفض؛ البحث/التصدير لا يسرّب.

---

## 5. قواعد الصلاحيات — Permission Rules

1. **مفاتيح أساسية (Canonical):** كل إجراء حساس له مفتاح صلاحية مستقر ومُبذر. ابحث في التعريفات القائمة قبل إنشاء مفتاح جديد؛ لا مرادفات.
2. **اتساق البذر:** الصلاحية تُعرف وتُبذر في `seed.ts` وتُطبق على الأدوار (SUPER_ADMIN والأدوار المخصصة) وترتبط بأذونات الشركة عند الاقتضاء.
3. **إخفاء الواجهة:** الواجهة تُخفي/تعطّل الإجراءات غير المصرح بها بناءً على صلاحيات المستخدم، لكن الحماية الحقيقية في backend.
4. **تفويض API:** كل نقطة نهاية تحمل `@Permissions(...)` وتُفحص؛ لا توجد نقطة نهاية محمية بالتعريف فقط.
5. **اختبار السماح/الرفض:** كل صلاحية جديدة تُختبر للمسموح والمرفوض.

---

## 6. قواعد التدقيق — Audit Rules

1. **سجل التدقيق:** كل إجراء حساس يُسجل: المستخدم، الموظف عند التوفر، الشركة، الفرع، نوع الكيان والمعرّف، الإجراء، الطابع الزمني، القيم القديمة/الجديدة، والسبب عند الطلب (إلغاء، تجاوز تكلفة، تغيير مسؤولية...).
2. **سجل سير العمل:** انتقالات الحالة عبر نقاط نهاية مخصصة تُسجل في التدقيق وفي حقل حالة/تاريخي للكيان (متى، من، إلى أي حالة، بأي سبب).
3. **تاريخ الكيان:** لا حذف مادي لسجلات معاملات حساسة دون استراتيجية (حذف ناعم `deletedAt` عند الاقتضاء مع الاحتفاظ بالسجل في التدقيق).
4. **وحدة التدقيق** الحالية (`audit-logs`) هي الوحيدة؛ تُستخدم من الخدمات ولا تُستبدل.

---

## 7. قواعد تجربة المستخدم — UX Rules

1. **مكونات مشتركة فقط:** أعد استخدام الموجود: نافذة الأخطاء، التوست، F9 الموحد، محولات البحث، أنماط الإجراءات الإدارية، أنماط الجداول، مكونات الكيانات، مكونات السياق التشغيلي، `ConfirmDialog`، `CmmsStatusBadge`... لا تُنشئ نمط واجهة منافس ثانٍ دون اعتماد صريح.
2. **حالات موحدة:** تحميل/فارغ/خطأ/ممنوع (loading/empty/error/permission) في كل قائمة وتفصيل ونموذج.
3. **منع الإرسال المكرر:** تعطيل أزرار الإرسال أثناء الطلب؛ معالجة استجابات متطابقة بأمان.
4. **الإجراءات الهدّامة:** تأكيد صريح قبل الحذف/الإلغاء؛ سبب إلزامي عند الحاجة.
5. **الإفصاح التدريجي:** إظهار الحقول حسب الحاجة، وليس كل الحقول دفعة واحدة.

---

## 8. قواعد الترجمة — i18n Rules

1. **كل ميزة تُرجم بالكامل** للعربية والإنجليزية معاً؛ لا نصوص مقسّية في مكونات أو وحدات تحكم أو خدمات أو تقارير أو استجابات تحقق.
2. **مزامنة المفاتيح:** أي مفتاح يُضاف يُضاف في الملفين `en` و`ar` (والنطاقات المعنية: common، والوحدة...). يُفحص التزامن في بوابات التحقق.
3. **لا مفاتيح خام:** لا يرى المستخدم `validation.x` أو `maintenance.y`؛ القيمة المترجمة تُعرض دائماً.
4. **RTL/LTR:** العربية تُختبر RTL والإنجليزية LTR لكل صفحة جديدة.

---

## 9. قواعد تقليل الإدخال — Reduced Input Rules

1. **أدخل مرة واحدة:** السياق التشغيلي (شركة/فرع/منشأة/وحدة تنظيمية/مخزن/وردية/مستخدم/موظف/تاريخ/وقت) يُملأ تلقائياً من الجلسة والسياق؛ التعديل يحمّل السجل نفسه ويُعبّئ كل الحقول القابلة للتحرير ولا ينشئ سجلاً جديداً.
2. **قيم افتراضية ذكية:** الحالة الابتدائية، الأرقام تلقائياً عبر خدمة الترقيم، الموقع/القسم/الخط من كيان الأب، الكميات/الأسعار من الملف الرئيسي عند الإمكان.
3. **التجسير:** الحقول المشتقة تلقائياً لا تُكرر كمدخلات يدوية مستقلة؛ التجاوزات تتطلب إذناً ومرئية ومُدققة (مع سبب للحساسة).
4. **القوالب والقيم السابقة:** عند إنشاء سجل جديد من سجل قائم، تُنقل القيم المعقولة (بعد التحقق من النطاق).
5. **اقتراحات ذكية وبحث:** استخدم F9 الموحد وقوائم البحث بدل حقول النص الحر للمراجع؛ دعم الباركود/QR حيثما يُستخدم في الوحدات القائمة.

---

## 10. قواعد الأعمال — Business Rules

1. **الصيانة:** لا تضعف السلوك المعاملاتي القائم: سجل الطلبات، التخصيصات، سجلات التوقف، مسؤولية القطع، سجل التركيب/الاستبدال، الجداول الوقائية وقوائم الفحص، الترقيم، معاملات صرف المخزون. صرف قطعة/تركيبها: تحقق التوافق (مستأجر/مخزن/آلة/مكوّن/أمر عمل)، تحقق الكمية المتاحة، منع الرصيد السالب، إنشاء حركة مخزون، تحديث الرصيد، تسجيل الطالب/المعتمد/الصارف/المستلم/المركّب/المستند المصدر وملكية التكلفة، تركيب وقطع المستبدل، كله بذرّية.
2. **المخزون:** لا تعديل رصيد بدون معاملة مصدر؛ الحركات تُرقم تلقائياً وتُسجل بتفاصيلها؛ التسويات بأسباب موثقة.
3. **الإنتاج:** لا يوجد بعد كمجال تشغيلي كامل — يُبنى تدريجياً بشرائح رأسية (بيانات رئيسية ← ورديات ← قدرات ← أوامر ← تشغيلات ← ناتج ← توقف/هالك ← استهلاك مواد ← سلع تامة ← جودة ← تكلفة ← OEE) ومتكامل مع الكيانات القائمة دون تكرار.
4. **التقارير والمؤشرات:** تُجمع من السجلات الذرية بفلترة مستأجر/تاريخ وترقيم صفحات أو دفق؛ لا حسابات كبيرة في المتصفح.

---

## 11. قواعد الاختبار — Testing Rules

1. **اختبارات ذات معنى** لكل تغيير تشغيلي بحسب الخطورة: وحدة لمنطق الأعمال، تكامل خدمة/قاعدة بيانات، تفويض API، عزل مستأجر، سماح/رفض صلاحية، انتقال حالة، ذرّية مخزون، إرسال مكرر، مرجع غير صالح، انحدار.
2. **لا** اختبارات فارغة، ولا skip لإخفاء فشل، ولا حذف اختبارات لتمرير البناء، ولا إضعاف تأكيدات، ولا محاكاة تُلغي القاعدة تحت الاختبار.
3. **تقرير صادق:** النتائج الفعلية تُعلن (نجاح/فشل/قبل الوجود) دون إخفاء.
4. **إثبات المتصفح** للعمليات الحرجة عند توفر الأدوات (مسار `واجهة → API → صلاحية → خدمة → قاعدة بيانات → تدقيق → نتيجة`).

---

## 12. قواعد الاكتشاف — Discovery Rules

1. **افحص أولاً:** قبل أي تغيير، افحص الكود الموجود ذي الصلة (نماذج، خدمات، صفحات، i18n، اختبارات، تقارير) وحدّد الوظائف القائمة.
2. **أعد الاستخدام:** ابنِ على الموجود؛ لا تُعد بناءً من الصفر.
3. **اكتشف التكرار:** حدد التطبيقات/المفاهيم المكررة قبل إنشاء ملفات جديدة، وأبلغ عنها.
4. **حافظ على السلوك العامل:** لا تكسر الوظائف القائمة؛ عند تغيير مشترك تحقق من كل المستخدمين.

---

## 13. عقد التنفيذ — Implementation Contract

1. **قاعدة البيانات:** نموذج/ترحيحات/فهارس/قيود آمنة وحافظة للبيانات، مراجعة عبر `prisma validate` وتوليد `prisma generate` عند الحاجة.
2. **الـ backend:** مصادقة، تفويض صلاحية، نطاق مستأجر/فرع، تحقق DTO مع رفض الحقول المجهولة، تحقق قواعد أعمال، حدود خدمة واضحة، معاملات، عقود أخطاء مستقرة، تدقيق للحساس، عدم تكرار إرسال حيثما أمكن، ترقيم صفحات/فلترة/فرز، وانتقالات حالة مخصصة.
3. **الـ frontend:** اتصال حقيقي بالـ API، CRUD كامل لنفس السجل، حالات تحميل/فارغ/خطأ/ممنوع، ترجمة كاملة، RTL/LTR، مكونات مشتركة، منع إرسال مكرر، تأكيد للهدّام.
4. **الاختبارات:** حسب القسم 11.
5. **الإثبات التشغيلي:** تشغيل المسار الحقيقي وإنشاء/قراءة/تعديل نفس السجل/انتقال حالة/رفض صلاحية/رفض مستأجر/أثر مخزون/أثر تكلفة/تدقيق/ترجمة/أخطاء، مع تقرير صادق.

---

## 14. بوابات التحقق — Validation Gates

قبل إعلان الاكتمال، يُنفذ بالترتيب:

1. مراجعة الملفات المعدلة.
2. اختبارات الوحدة المركزة.
3. اختبارات التكامل/API المركزة.
4. `prisma validate` عندما يتعلق بـ schema.
5. `prisma generate` عند الحاجة.
6. فحص أنواع الـ backend (`tsc --noEmit`).
7. فحص أنواع الـ web.
8. بناء الـ web (`next build`).
9. فحص اتساق i18n (مفاتيح en/ar متزامنة، لا مفاتيح خام).
10. إثبات المتصفح المركز للعمليات الحرجة (حيثما أمكن).
11. `git diff --check`.
12. `git status` نهائي.

لا تُخفى فشل سابق؛ تُفصل: فشل جديد / فشل سابق / تحذيرات / غير مُتحقق.

---

## 15. قواعد نقاط التفتيش — Checkpoint Rules

1. **نقطة تفتيش مستقلة:** عند نقاط حدودية (نهاية مرحلة/شريحة) يُكتب تقرير إثبات في `docs/proofs/` يُسجل الحقائق والأدلة والقيود، ولا يُعتد بالبناء الناجح وحده كدليل.
2. **التحقق قبل المتابعة:** لا يُنتقل لمرحلة/شريحة جديدة قبل مراجعة إثبات السابقة (المادة 3-4 من الخطة الرئيسية).
3. **انضباط Git:** سجّل قبل العمل: الفرع والالتزام والملفات المعدلة وغير المتعقبة؛ لا تُدرج مخرجات البناء/الأسرار/الملفات المؤقتة؛ لا force-push؛ الالتزام فقط عند الطلب الصريح مع رسالة موجزة بأسلوب المستودع (conventional commits).
4. **تقارير الإثبات** موثقة بتاريخ ونتيجة صادقة (`COMPLETE`/`PARTIAL`/`BLOCKED`/`NOT_VERIFIED`).

---

## 16. عقد التقرير النهائي — Final Response Contract

عند نهاية أي مهمة تنفيذ، أبلغ بموضوعات الخطة الـ 19 من `AGENTS.md`:

1. حالة المهمة.
2. النطاق الدقيق المكتمل.
3. الملفات المنشأة.
4. الملفات المعدلة.
5. نماذج/ترحيحات قاعدة البيانات.
6. نقاط نهاية API المضافة/المعدلة.
7. مسارات الواجهة المضافة/المعدلة.
