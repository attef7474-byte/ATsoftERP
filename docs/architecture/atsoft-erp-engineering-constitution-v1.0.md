## مقدمة — الغرض والنطاق

هذا الدستور هو **القانون الهندسي الملزم** لكل عمل في ATsofterp. لا يجوز لأي مؤشر اصطناعي أو مهندس أو أمر مهمة تجاوز قواعده إلا بحكم مهمة صريح يحدد أن الإعفاء مقصود، وبشرط ألا يُسبب فقدان بيانات أو اختراق أمان أو كسراً لرقابة متعددة الشركات أو إتلافاً لحالة تشغيلية.

الغرض من الدستور ليس إبطاء التطوير، بل جعل **الجودة، والتتبع، والصلاحية التشغيلية** بنيةً أساسية يبني عليها الجميع، بدلاً من أن تكون زينة تُضاف في النهاية.

يُقرأ الدستور مع ثلاث مرجعيات رئيسية:

1. `AGENTS.md` — الملخص التشغيلي السريع للأوامر الآلية (يتيح الإشارة إلى هذا الدستور).
2. `docs/architecture/operational-vision.md` — الرؤية التشغيلية الطويلة للمنتج.
3. `docs/proofs/atsofterp-current-architecture-discovery-report.md` — الاكتشاف المعماري الحالي.

## المادة 1: هوية المشروع والخط المبدئي

| البند | القيمة |
|---|---|
| اسم المنتج | `ATsofterp` |
| الاسم التجاري المرن | ATsoft ERP |
| نوع النظام | نظام تشغيلي متعدد الشركات للصيانة، والإنتاج، والأصول، والمخزون، وقطع الغيار، والتكاليف التشغيلية، وتنظيم المصنع، والعمليات اليومية |
| واجهة المستخدم | عربية + إنجليزية |
| الاتجاهات | RTL وLTR |
| الواجهة البرمجية | NestJS API |
| الواجهة الأمامية | Next.js App Router |
| قاعدة البيانات | SQL Server |
| ORM | Prisma |
| اللغة | TypeScript |
| التحكم بالوصول | JWT + صلاحيات قائمة على الأدوار (RBAC) |
| بيئة التشغيل | محلي على Windows |
| الحاويات | لا Docker في الخط الأساسي الحالي المعتمد إلا إذا تغيّر ذلك صراحةً لاحقاً |

### 1.1 مبادئ عدم التكرار

1. المستودع يحتوي بالفعل على تنفيذ كبير ومُشغَّل لـ: الصيانة، والمخزون، والأصول، والتقارير، والإعدادات، والتدقيق، والإشعارات، والمرفقات، والباركود، والوظائف الإدارية.
2. لا تتعامل مع المستودع كمشروع جديد.
3. لا تعِد بناء وحدات موجودة تعمل إلا إذا كانت المهمة تتطلب بشكل صريح ترحيلاً مبرراً أو استبدالاً.
4. الكود الحالي هو **مصدر الحقيقة النهائي** (source of truth). التقارير السابقة أدوات استكشاف ولا تتجاوز التنفيذ الحالي.

## المادة 2: الأهداف الأولية للمنتج

كل تنفيذ يجب أن يخدم الأهداف التالية:

1. استخدام تشغيلي حقيقي في الشركات والمصانع.
2. عزل قوي متعدد الشركات ومتعدد الفروع.
3. حد أدنى من إدخال البيانات اليدوية اليومية.
4. إعادة استخدام تلقائية للمعلومات المخزنة سابقاً.
5. سير عمل واضح وبسيط للمستخدمين غير التقنيين.
6. إعدادات مرنة لشركات ذات هياكل مختلفة.
7. تتبع كامل للإجراءات التشغيلية ذات الأثر المالي.
8. تكامل موثوق بين الصيانة والمخزون وقطع الغيار والإنتاج.
9. تقارير دقيقة دون ازدواج في الإجماليات.
10. توسيع آمن دون كسر الوحدات القائمة.

لا تحسّن فقط سرعة توليد الكود. حسّن من أجل:

- الصحة التشغيلية.
- سلامة البيانات.
- تقليل الجهد على المستخدم.
- قابلية الصيانة.
- قابلية الاختبار.
- الأمان.
- التتبع.
- قابلية التوسع طويلة المدى.

## المادة 3: قاعدة الواقع غير القابلة للتفاوض

يجب أن يحتوي ATsofterp على وظائف حقيقية، متصلة، قادرة على الإنتاج.

**المحظورات الصريحة:**

- بيانات تشغيلية مزيفة (mock operational data).
- صفحات وهمية (fake pages).
- صفحات عرض فقط تُقدَّم كعمل مكتمل.
- استجابات نجاح ثابتة (static success responses).
- أزرار دون معالجات حقيقية.
- نماذج لا تُحفظ عبر API حقيقي.
- APIs غير متصلة بعمليات قاعدة بيانات حقيقية.
- خدمات أو وحدات تحكم أو DTOs أو اختبارات أو صفحات فارغة.
- وحدات برمجية زائفة تُقدَّم كمطبَّقة.
- سجلات تشغيلية مكتوبة يدوياً في الكود.
- مسارات بديلة صامتة تخفي غياب وظائف الـ backend.
- كتل catch تكبت الأخطاء.
- تعطيل التحقق أو الاختبارات لجعل البناء يمر.
- الادعاء بالاكتمال اعتماداً على الترجمة فقط.

الميزة ليست مكتملة لأن الملفات موجودة. الميزة مكتملة فقط عندما تكون قاعدة البيانات، والـ backend، والصلاحيات، والـ frontend، والترجمات، والاختبارات، وتدفق التشغيل **متصلة ومتحقق منها**.

## المادة 4: انضباط تنفيذ المهمات

لكل مهمة تنفيذ:

1. اقرأ نطاق المستخدم بعناية.
2. افحص الكود الحالي ذي الصلة أولاً.
3. حدد التنفيذ القائم وأعد استخدام أنماطه الراسخة.
4. اكتشف التطبيقات المكررة أو القديمة قبل إنشاء ملفات جديدة.
5. حدد أصغر حدود تنفيذ آمنة تحقق النتيجة المطلوبة بالكامل.
6. نفّذ الشريحة الرأسية الكاملة (vertical slice).
7. نفّذ التحقق المركز أولاً.
8. نفّذ التحقق الأوسع المطلوب.
9. راجع الـ diff النهائي.
10. اكتب الأدلة الدقيقة.

لا تفحص المستودع كاملاً بشكل متكرر عندما تكون البنية المطلوبة معروفة. لا تتوقف بعد التخطيط عندما تطلب المهمة تنفيذاً. لا تطرح أسئلة يمكن حلها من الكود القائم أو الأنماط أو العلاقات أو الصفحات أو سلوك الـ API أو التقارير.

اسأل سؤالاً فقط عندما يهدد قرار غير محسوم فعلياً: فقدان بيانات، أو كشف بيانات عبر الشركات، أو ترحيلاً مدمراً، أو محاسبة خاطئة، أو سلوك سير عمل غير قابل للتراجع، أو كسر بيانات إنتاج قائمة.

عندما تتوفر افتراضات آمنة، استخدمها ووثّقها.

## المادة 5: ضبط النطاق

عدّل فقط الملفات المطلوبة للمهمة الحالية.

**لا تفعل:**

- أعد هيكلة وحدات غير مرتبطة.
- أعد تسمية نماذج أو مسارات غير مرتبطة.
- أعد تنسيق المستودع كاملاً.
- فعّل مجالات مرفوضة أو غير نشطة.
- أضف تمويلاً أو مبيعات أو مشتريات أو رواتب HR أو AI أو IoT أو BI أو تنبؤات أو أي نطاق غير معتمد إلا إذا طُلبت صراحةً.
- أنشئ وحدات مستقبلية تخمينية.
- أنشئ ملفات لا يستخدمها التشغيل المطبق.

عندما تكون التغييرات المجاورة ضرورية للصحة، اشرح سبب ضرورتها.

تجنّب الطرفين:

- لا تصنع رقعة ملف واحد غير مكتملة عندما يكون التغيير الشامل مطلوباً.
- لا تنفذ إعادة هيكلة شاملة للمستودع من أجل متطلب محلي.

## المادة 6: الحفاظ على الوحدات القائمة وتوسيعها

تحتوي الوحدات القائمة على عمل كبير: الصيانة، والمخزون، والماكينات، وقطع الغيار، والأجزاء المثبتة، وتاريخ الاستبدال، وأوامر الإصلاح، والتقارير، والبحث، والترقيم، والإعدادات، والإشعارات، والتدقيق، والمرفقات.

قبل تغيير مجال قائم:

- تتبّع المسار الحالي من الـ frontend إلى قاعدة البيانات.
- حدد الصلاحيات الحالية.
- حدد انتقالات الحالة الحالية.
- حدد سلوك الترقيم الحالي.
- حدد سلوك التدقيق الحالي.
- حدد التكاملات الحالية.
- حدد البيانات القائمة التي قد تتطلب ترحيلاً.
- أضف اختبارات انحدار قبل التغييرات الخطرة أو معها.

فضّل التوسيع الآمن على الاستبدال. لا تُنشئ بدائل موازية لمفاهيم قائمة إلا إذا اعتمدت المهمة خطة ترحيل.

**أمثلة على التكرار المحظور:**

- نموذج طلب صيانة ثانٍ.
- سير عمل أجزاء مثبتة ثانٍ.
- نظام أرصدة مخزون ثانٍ.
- خدمة ترقيم ثانية.
- نظام بحث موحد ثانٍ.
- نظام معالجة أخطاء ثانٍ.
- مفاتيح صلاحيات مكررة لنفس الإجراء.
- مفردات حالة مكررة لنفس الكيان.

## المادة 7: ثوابت تعدد الشركات والفروع

عزل تعدد الشركات **حد أمني إلزامي**، وليس فلتراً اختيارياً في الواجهة.

- لكل كيان تشغيلي مملوك للمستأجر مالك شركة واضح.
- لكل كيان مملوك لفرع مالك فرع واضح.
- تُفضَّل حقول الملكية المباشرة للسجلات التشغيلية الحرجة حتى لو أمكن استنتاج الملكية عبر العلاقات.
- السجلات العامة/المشتركة مسموحة فقط عند تصميمها وتوثيقها واعتمادها عمداً.

لكل عملية إنشاء/قراءة/تحديث/حذف/بحث/تقرير/تصدير/طباعة/مرفق/إشعار/تدقيق/عملية خلفية:

- فرض نطاق الشركة في الـ backend.
- فرض نطاق الفرع عند الاقتضاء.
- لا تعتمد فقط على header أو حقل مخفي في الواجهة.
- لا تثق بشركة/فرع من العميل دون تحقق من الصلاحية.
- لا تجلب بالـ `id` فقط لسجلات مملوكة للمستأجر.
- أدرج نطاق المستأجر في الاستعلامات المباشرة للسجلات.
- تحقق أن جميع السجلات المرجعية تنتمي لسياقات شركة وفرع متوافقة.
- امنع العلاقات عبر الشركات وعبر الفروع غير المصرح بها.
- امنح القيود الفريدة نطاقاً مناسباً.
- امنح تسلسلات الترقيم نطاقاً مناسباً.
- امنح نتائج البحث والتصدير نطاقاً مناسباً.
- امنح المرفقات وسجلات التدقيق نطاقاً مناسباً.
- اختبر التلاعب بمعرفات عبر الشركات.

لعمليات الكتابة يجب أن يكون السياق التشغيلي النشط صالحاً ومصرحاً به. غياب السياق يجب ألا يوسّع الوصول بصمت.

سلوك SUPER_ADMIN يجب أن يكون صريحاً ومُدققاً. لا تستخدم سلوك SUPER_ADMIN لإخفاء غياب فرض المستأجر للأدوار العادية.

## المادة 8: مرونة التنظيم والمصنع

ابقِ هذه البنى منفصلة مفهوماً:

1. التنظيم القانوني والإداري.
2. الطوبولوجيا التشغيلية للمصنع.
3. تخصيصات القوى العاملة والإشراف.
4. تسلسل مراكز التكلفة.
5. تفويض المستخدم ونطاق البيانات.

لا تُحمّل جدولاً واحداً لتمثيل البنى الخمس معاً.

يجب أن يدعم النظام شركات مختلفة بأعماق وأسماء مختلفة. لا تضع افتراضات مكتوبة مثل:

- كل شركة لها أربعة فروع بالضبط.
- كل مصنع له قسم رقائق وفشار فقط.
- كل منطقة لها تصنيع وتعبئة فقط.
- كل خط له ست ماكينات بالضبط.
- كل إدارة لها قسمان بالضبط.
- كل شركة تستخدم نفس التسلسل الهرمي للتقارير.

يجب أن تسمح البنية:

- أعداد متغيرة من الشركات والفروع.
- عمق تنظيمي متغير.
- إدارات متكررة أو وحدات تنظيمية متكررة معتمدة.
- مناطق مصنع وأقسام عمليات متغيرة.
- أعداد متغيرة من خطوط الإنتاج.
- أعداد متغيرة من الماكينات والمكونات.
- تخصيصات مؤقتة ودائمة للموظفين.
- نطاقات مسؤولية متعددة.
- مصطلحات وإعدادات خاصة بالشركة.

لا تضعف مرونة الإعداد النزاهة التراجعية. استخدم بيانات مرجعية قابلة للإعداد من أجل: الأنواع، والفئات، والأسباب، والأولويات، والتصنيفات، والقوالب، والعتبات، والجداول، والحقول الاختيارية، وإعدادات العرض.

احتفظ بالقواعد التراجعية الحرجة مكتوبة ومحكمة في الكود. لا تحوّل سلامة المخزون أو الإنتاج أو الصيانة أو التكاليف أو الموافقات إلى إعداد JSON غير منضبط.

## المادة 9: الحد الأدنى من إدخال البيانات والتعبئة التلقائية

القاعدة الأساسية:

> أدخل المعلومات مرة واحدة، وأعد استخدامها في كل مكان بأمان.

يجب أن تطلب النماذج التشغيلية اليومية فقط المعلومات التي لا يمكن للنظام اشتقاقها بموثوقية.

**تُشتق وتُعبأ تلقائياً حيثما أمكن:**

- الشركة، والفرع، والمنشأة، والوحدة التنظيمية، ومنطقة الإنتاج، وقسم العمليات، وخط الإنتاج، والماكينة، ومكوّن الماكينة، ونوع العملية، ومركز التكلفة، والمخزن، والوردية، والمستخدم الحالي، والموظف الحالي، والتاريخ والوقت، ورقم المستند، والحالة الأولية، وفريق الصيانة المسؤول، ومسؤولية الخط المعينة، ووحدة المنتج، والافتراضيات الخاصة بالمنتج أو الماكينة، والطلب أو بيانات الطلب المرتبطة، والتوافق المعروف لقطع الغيار، وبيانات الماكينة والمكوّنات القائمة.

**أمثلة:**

- اختيار ماكينة يملأ شركتها وفرعها وخطها ومنطقتها وقسمها ومركز التكلفة الافتراضي ونوع العملية ونطاق الصيانة ذا الصلة.
- فتح طلب صيانة من صفحة ماكينة يملأ الماكينة والتسلسل الهرمي.
- فتح طلب من انقطاع إنتاج يملأ تشغيل الإنتاج النشط والمنتج والوردية والخط والماكينة ووقت بدء الانقطاع.
- اختيار قطعة غيار يعرض الماكينات/المكونات المتوافقة، والمخزون المتاح، والمخزن، والحالة، والاستخدام الأخير.
- اختيار أمر إنتاج يملأ المنتج والمسار المعتمد وBOM والكمية المستهدفة والمعدل المستهدف والخط والوحدة.
- تحرير سجل يجب أن يحمّل نفس السجل القائم ويملأ كل الحقول القابلة للتحرير.
- يجب أن تدعم المعاملات المتكررة القوالب والنسخ من السابق والافتراضيات المنضبطة.

**الحقول المشتقة تلقائياً لا تُكرر كمدخلات يدوية مستقلة.**

عندما يجوز تغيير حقل مُعبأ تلقائياً:

- فقط المستخدمون المصرح لهم قد يعيدون كتابته.
- يجب أن يكون التجاوز مرئياً.
- قد يكون السبب مطلوباً للتجاوزات الحساسة.
- يجب تدقيق القيمة السابقة والجديدة.

لا تُعبأ بيانات قديمة من سجل سابق غير مرتبط. يجب أن تكون الافتراضيات محدودة بالمستخدم والشركة والفرع وسير العمل والكيان الحاليين.

## المادة 10: معايير النماذج وسير العمل

استخدم الكشف التدريجي (progressive disclosure). اعرض فقط الحقول المطلوبة للعملية والحالة الحالية.

افصل: الحقول الأساسية، والتفاصيل الاختيارية، والحقول المتقدمة، وحقول التدقيق والنظام.

لا تعرض معرفات النظام كمُعرِّفات للمستخدم عندما توجد أسماء أو أكواد قابلة للقراءة.

استخدم عمليات بحث قابلة للبحث (searchable lookups) لمجموعات البيانات المرجعية الكبيرة. أعد استخدام أنماط F9 الموحدة والبحث الحالية بدلاً من منقّيات غير متسقة.

يجب أن تتضمن كل صفحة تشغيلية، عند الاقتضاء:

- حالة تحميل، وحالة فارغة، وحالة خطأ، وحالة صلاحية، وتفسير الحالة المعطّلة، وتغذية راجعة نجاح.
- بحث، وترشيح، وترقيم صفحات أو virtualisation للمجموعات الكبيرة.
- حالة حالية واضحة، والإجراءات التالية المسموحة، والوصول إلى التدقيق/السجل، والمرفقات حيثما كان ذا صلة تشغيلية.
- منع الإرسال المكرر.
- تعطيل أزرار الإجراء أثناء تشغيل الطلبات.
- الحفاظ على البيانات المدخلة عند حدوث خطأ API قابل للاسترداد.
- تأكيد للإجراءات المدمرة أو غير القابلة للتراجع.
- لا تطلب من المستخدمين إعادة إدخال المعلومات المخزنة في الماكينة/الخط/المنتج/الطلب/الموظف/المخزن/السياق التشغيلي المحدد.

---

## المادة 11: سلامة قاعدة البيانات

قاعدة البيانات SQL Server وتحوي بيانات مهمة موجودة.

**لا تنفّذ ولا توصي أبداً بـ:**

- `prisma migrate reset`
- حذف قاعدة البيانات.
- اقتطاع الجداول (truncation).
- إعادة تعيين مدمرة.
- `prisma db push` دون مراجعة.
- تحرير ترحيل مطبق بالفعل.
- حذف سجل الترحيلات.
- إعادة إنشاء قاعدة البيانات لحل مشكلة schema.
- حذف أو تحديث غير محدد النطاق.

استخدم ترحيلات مراجَعة. للتغييرات الحساسة على البنية استخدم ترحيلات مرحلة:

1. أضف بنية قابلة للتأجيل أو متوافقة مع الخلف.
2. عبّئ السجلات القائمة (backfill).
3. تحقق من التعبئة.
4. أضف القيود المطلوبة.
5. حدّث سلوك التطبيق.
6. أزل البنية المهجورة فقط في مهمة منفصلة معتمدة.

يجب أن يوضح كل ترحيل:

- أثر البيانات القائمة.
- الافتراضي أو سلوك التعبئة.
- نهج التراجع/الاسترداد.
- أثر الفهارس.
- أثر المستأجرين.
- توافق وقت التشغيل.

استخدم معاملات قاعدة البيانات للعمليات متعددة السجلات. يجب أن تكون: المخزون، والتكلفة، والتركيب، والاستبدال، وترحيل الإنتاج، وانتقالات سير العمل ذرية حيث يؤدي الاكتمال الجزئي إلى إفساد البيانات.

استخدم تخزيناً مناسباً من نوع `Decimal` للنقود والكميات الدقيقة. لا تستخدم أرقام فاصلة عائمة للحقيقة النقدية.

أضف فهارس لمسارات الاستعلام الحقيقية، ومرشحات المستأجر، والمفاتيح الأجنبية، ومرشحات الحالة، ونطاقات التاريخ. لا تضف فهارس دون فهم أثر الكتابة والتخزين.

## المادة 12: سلامة البيانات والقيم المشتقة

لا تخزّن نفس المبلغ التجاري كحقائق مستقلة منفصلة في كل مستوى من التسلسل الهرمي.

سجّل المعاملة الذرية مرة واحدة بكل الأبعاد المطلوبة، ثم اجمعها في التقارير.

**أمثلة:**

- معاملة تكلفة قطع غيار واحدة قد تُرجع بواسطة: الماكينة، الخط، القسم، المنطقة، الفرع، وإدارة الصيانة.
- لا تُنشئ ست معاملات تكلفة منفصلة لنفس العطل الفيزيائي.
- يجب ألا يُجمع ناتج الإنتاج من ماكينات متسلسلة كما لو أن كل ماكينة أنتجت سلعاً نهائية مستقلة.
- يجب أن يأتي الناتج النهائي للخط من نقطة قياس معتمدة أو قاعدة تجميع معرفة.
- يجب ألا يُعدَّ ناتج التصنيع وناتج التعبئة مرتين كمنتج نهائي واحد.

يجب أن تأتي الإجماليات المشتقة من سجلات مصدر موثوقة. يُسمح بالإجماليات المخزنة مؤقتاً فقط مع استراتيجية تسوية موثقة.

يجب أن يكون لكل كمية وتكلفة ومدة توقف وانتقال حالة مصدر حقيقة واضح.

---

## المادة 13: معايير الـ Backend

يجب أن تتضمن كل عملية backend جديدة أو معدلة:

- المصادقة ما لم تكن عامة صراحةً.
- فرض الصلاحية في الـ backend.
- التحقق من المستأجر والفرع.
- تحقق DTO.
- رفض الحقول غير المعروفة.
- تحقق من قواعد العمل.
- حدود خدمة واضحة.
- معاملات صحيحة.
- عقود أخطاء مستقرة.
- تدقيق الإجراءات الحساسة.
- منع التكرار (idempotency) حيثما كان الإرسال المتكرر ممكناً.
- ترقيم صفحات للمجموعات الكبيرة المحتملة.
- ترشيح وفرز حيثما يلزم تشغيلياً.
- فرض متسق لانتقالات الحالة.

تبقى وحدات التحكم رقيقة. تنتمي قواعد العمل إلى الخدمات أو السياسات المختصة بالمجال، وليس مكررة عبر وحدات التحكم.

لا تثق بالتحقق الأمامي. لا تعرض القيم السرية أو كلمات المرور أو الرموز أو قيم الأمان الداخلية. لا تُرجع استثناءات قاعدة البيانات الخام للمستخدمين.

استخدم مفاتيح أخطاء مترجمة متسقة أو تنسيق الخطأ المعتمد في المشروع.

يجب أن يتحقق انتقال الحالة من: الحالة الحالية، والحالة المطلوبة، وصلاحية المستخدم، ونطاق المستأجر، والبيانات المطلوبة، وحالة السجلات المرتبطة، وأثر المخزون أو الإنتاج، وبيانات التدقيق.

لا تحدّث الحالة عبر نقطة تحرير عامة غير مقيدة عندما يكون انتقال مخصص مطلوباً.

---

## المادة 14: معايير الـ Frontend

يجب أن تستخدم كل عملية frontend الـ API الحقيقي للـ backend.

يتطلب تدفق CRUD كامل:

- قائمة حقيقية، وتفاصيل حقيقية، وإنشاء حقيقي، وتحرير حقيقي لنفس السجل، وحذف/تعطيل حقيقي حيثما سُمح.
- فحوص صلاحية حقيقية.
- تحميل ومعالجة أخطاء حقيقيان.
- حالات فارغة حقيقية.
- ترجمات عربية وإنجليزية.
- تحقق RTL وLTR.

استخدم `POST` للإنشاء ونمط `PATCH /:id` المعتمد لتحديث نفس السجل. يجب أن تجلب صفحات التحرير السجل القائم وتضعه في النموذج. يجب ألا ينشئ التحرير سجلاً جديداً أبداً.

لا تستخدم خيارات تشغيلية مكتوبة يدوياً عندما يوجد API أو جدول مرجعي قابل للإعداد. لا تُظهر إجراءات لا يستطيع المستخدم الحالي تنفيذها. لا يحل إخفاء الصلاحية في الـ frontend محل فرضها في الـ backend.

أعد استخدام المكونات المشتركة القائمة: نافذة الخطأ، والـ toasts، وبحث F9 الموحد، ومحولات البحث، وأنماط الإجراءات الإدارية، وأنماط شبكات البيانات، ومكوّنات الكيانات، ومكوّنات السياق التشغيلي. لا تُنشئ نمط واجهة منافساً ثانياً دون اعتماد صريح.

---

## المادة 15: العربية والإنجليزية وRTL وLTR

يجب أن يدعم كل ميزة موجهة للمستخدم العربية والإنجليزية.

لا تضع نصاً موجهاً للمستخدم في مكوّنات أو وحدات تحكم أو خدمات أو تقارير أو استجابات تحقق. أضف مفاتيح ترجمة مطابقة للغتين. يجب أن تبقى مجموعات مفاتيح الترجمة متزامنة.

يجب اختبار العربية في RTL والإنجليزية في LTR. تحقق من: محاذاة النماذج، والجداول، واتجاه النوافذ، والأيقونات، والأرقام، والتواريخ، والترقيم، والألواح الجانبية، وتخطيطات الطباعة، وتسميات التصدير، ورسائل الخطأ، والحالات الفارغة، وتسميات الحالة، وتسميات الإجراءات.

لا تُرجع مفاتيح ترجمة خام للمستخدم.

---

## المادة 16: الصلاحيات والتدقيق والمساءلة

يتطلب كل إجراء حساس مفتاح صلاحية مستقراً ومُبذوراً.

قبل إنشاء صلاحية: ابحث في تعريفات الصلاحيات القائمة، ووحدات التحكم، واستخدام الـ frontend، وملفات البذر. تجنّب المترادفات والاختلافات.

لا تكتمل الصلاحية حتى:

- تُعرَّف وتُبذر وتُفرض في الـ backend وتُستخدم بشكل صحيح في الـ frontend وتُترجم حيث تُعرض وتُختبر للأدوار المسموحة والمرفوضة.

**دوّن (audit) الإجراءات الحساسة:**

- الإنشاء، والتحديث، والحذف/التعطيل، والموافقة، والرفض، والإلغاء، وانتقالات الحالة، وترحيل المخزون، وصرف قطع الغيار، وتركيب الأجزاء وإزالتها، وتجاوز التكلفة، وتجاوز المستأجر/الفرع، وتغيير التخصيصات، وترحيل الإنتاج، وتغيير ملكية التوقف.

يجب أن تتضمن بيانات التدقيق: المستخدم، والموظف حيثما توفر، والشركة، والفرع، ونوع الكيان، ومعرف الكيان، والإجراء، والطابع الزمني، والقيم السابقة ذات الصلة، والقيم الجديدة ذات الصلة، والسبب حيثما طُلب.

---

## المادة 17: حماية الصيانة والمخزون

لا تُضعف السلوك التراجعية القائم للصيانة والمخزون.

**لأعمال الصيانة حافظ على:**

- سجل الطلبات، والتخصيصات، وسجلات التوقف، ومسؤولية القطع، وسجل الأجزاء المثبتة والاستبدال، وجداول الوقاية وقوائم الفحص، والترقيم، ومعاملات صرف المخزون.

**لصرف قطع الغيار وتركيبها:**

- تحقق من توافق المستأجر والمخزن والماكينة والمكوّن وأمر العمل.
- تحقق من الكمية المتاحة.
- امنع الرصيد السالب.
- أنشئ حركة مخزون.
- حدّث رصيد المخزون.
- سجّل الطالب والموافق والمصرف والمستلم والمركّب والماكينة والمكوّن والمستند المصدر كما يلزم.
- سجّل ملكية التكلفة.
- سجّل التركيب والقطعة المستبدلة.
- نفّذ التحديثات التابعة بشكل ذري.

لا تحرّر رصيد مخزون مباشرة دون معاملة مصدر مصرح بها.

---

## المادة 18: مبادئ وحدة الإنتاج

وحدة الإنتاج غير موجودة حالياً كمجال تشغيلي كامل. ابنها تدريجياً كشرائح رأسية مختبرة. لا تنشئ مجال الإنتاج كله دفعة واحدة غير منضبطة.

**الترتيب الموصى به:**

1. البيانات الرئيسية للإنتاج المطلوبة للتنفيذ.
2. الورديات والتخصيصات التشغيلية.
3. معايير قدرة المنتج.
4. أوامر الإنتاج.
5. جلسات/تشغيلات التنفيذ.
6. تسجيل ناتج الماكينات والخطوط.
7. أسباب التوقف والخسارة.
8. الهالك وإعادة العمل.
9. صرف واستهلاك المواد.
10. استلام السلع التامة.
11. تكامل الجودة.
12. تكامل التكاليف.
13. تقارير OEE والأداء.

يجب أن يتكامل الإنتاج مع القائمة: الشركات، الفروع، البنية التنظيمية، خطوط الإنتاج، الماكينات، مكونات الماكينات، المخازن، المنتجات، مراكز التكلفة، طلبات الصيانة، التوقف، الإشعارات، التدقيق، الترقيم، البحث، المرفقات.

لا تكرر الكيانات القائمة فقط لتبسيط تطوير الإنتاج.

---

## المادة 19: الاختبارات إلزامية

وجود ملف اختبار فارغ ليس اختباراً. يجب أن يضيف كل تغيير تشغيلي اختبارات ذات معنى متناسبة مع خطره.

**الفئات المطلوبة:**

- اختبارات وحدة قواعد العمل.
- اختبارات تكامل الخدمة/قاعدة البيانات.
- اختبارات ترخيص API.
- اختبارات عزل المستأجر.
- اختبارات السماح/الرفض للصلاحيات.
- اختبارات انتقال الحالة.
- اختبارات ذرّية المخزون.
- اختبارات الإرسال المكرر.
- اختبارات المرجع غير الصالح.
- اختبارات انحدار للأعطال المُصلحة.
- اختبارات تفاعل/متصفح لسير العمل الحرجة.

**للكيانات المملوكة للمستأجر اختبر على الأقل:**

- الشركة A تستطيع الوصول لسجلها.
- الشركة B لا تستطيع قراءته بالـ id.
- الشركة B لا تستطيع تحريره بالـ id.
- الشركة B لا تستطيع الإشارة إليه في معاملة جديدة.
- يُرفض وصول الفرع غير المصرح به.
- لا يُسرّب البحث والتصدير السجل.

**لا تفعل:** إضافة مواصفات فارغة، أو تخطي اختبارات فاشلة دون اعتماد موثق، أو حذف اختبارات لتمرير التحقق، أو إضعاف التأكيدات، أو محاكاة قاعدة العمل محل الاختبار، أو الادعاء بالنجاح دون إظهار النتائج الفعلية.

---

## المادة 20: ترتيب التحقق

استخدم التحقق المركز أولاً لتقليل الوقت الضائع، ثم نفّذ الفحوص الأوسع المطلوبة.

**الترتيب النموذجي:**

1. افحص الملفات المعدلة.
2. نفّذ اختبارات الوحدة المركزة.
3. نفّذ اختبارات التكامل/API المركزة.
4. نفّذ تحقق Prisma عند الارتباط بالـ schema.
5. نفّذ توليد Prisma عند الحاجة.
6. نفّذ فحص أنواع الـ API أو البناء.
7. نفّذ فحص أنواع الـ Web.
8. نفّذ بناء الـ Web.
9. نفّذ فحص اتساق i18n.
10. نفّذ إثبات المتصفح المركز.
11. افحص `git diff --check`.
12. افحص `git status` النهائي.

لا تُعد البناء الكامل بعد كل تعديل صغير. نفّذه عندما تكون دفعة التنفيذ المتماسكة جاهزة.

لا تخفِ أبداً الفشل المسبق. افصل بوضوح: الفشل الجديد من المهمة، والفشل المسبق، والتحذيرات، والمناطق غير المتحقق منها.

---

## المادة 21: الإثبات التشغيلي

البناء الناجح ليس إثباتاً كافياً لميزة تشغيلية.

لسير عمل حرج أثبت المسار الحقيقي:

`Frontend → API → Permission → Service → Database → Audit → Result`

حيثما أمكن تحقق من: الإنشاء، والقراءة، وتحرير نفس السجل، وانتقال الحالة، ورفض الصلاحية، ورفض المستأجر، وأثر المخزون، وأثر التكلفة، وحدث التدقيق، وواجهة عربية، وواجهة إنجليزية، ومعالجة الأخطاء، ومنع التكرار.

لا تُبلّغ عن `COMPLETE` عندما لا يُتحقق من الربط التشغيلي. استخدم بأمانة: `COMPLETE` / `PARTIAL` / `BLOCKED` / `NOT_VERIFIED`.

---

## المادة 22: سلامة Git والمستودع

لا تنفّذ عمليات كتابة Git ما لم تطلبها المهمة الحالية صراحةً.

لا تقم تلقائياً بـ: الالتزام، أو الدفع، أو الدمج، أو إعادة الأساس، أو إعادة التعيين، أو التنظيف، أو حذف الملفات غير المتعقبة، أو إنشاء/نقل العلامات، أو تبديل الفروع.

قبل العمل سجّل: الفرع الحالي، والالتزام الحالي، والملفات المعدلة القائمة، والملفات غير المتعقبة القائمة.

لا تكتب فوق تغييرات المستخدم السابقة. لا تدّعِ شجرة نظيفة عندما تكون ملفات الإثبات المولَّدة بالمهمة موجودة. لا تضمّن القطع الأثرية المولدة/المبنية/المخزنة/السجلية/السرية/المؤقتة في الالتزامات. لا تدفع قسراً.

---

## المادة 23: الأسرار وملفات البيئة

لا تعرض أو تلتزم أبداً: بيانات اعتماد قاعدة البيانات، وأسرار JWT، ومفاتيح API، وكلمات مرور SMTP، والرموز، والشهادات الخاصة، وكلمات مرور المستخدمين، وسلاسل اتصال الإنتاج.

لا تعرض قيم الأسرار في التقارير. استخدم `REDACTED`. اقرأ `.env.example` حيثما لزم. لا تقرأ ملفات `.env` الحقيقية إلا إذا طلبت المهمة تشخيصاً آمناً للإعداد وأذنت بذلك. لا تعدّل ملفات البيئة دون تعليمات صريحة.

---

## المادة 24: الأداء وقابلية التوسع

تجنّب استعلامات القوائم غير المحدودة. استخدم ترقيم الصفحات وانتقاء الحقول المستهدفة. امنع أنماط N+1. استخدم فهارس محاذية للمرشحات الحقيقية. لا تحمّل أجسام المرفقات الكاملة أو السجلات الطويلة في نقاط نهاية القوائم العادية. لا تحسب التجميعات الكبيرة في المتصفح عندما تنتمي إلى الـ backend أو قاعدة البيانات. لا تضف تخزيناً مؤقتاً قبل تعريف إبطاله وعزل المستأجر.

للتقارير: طبّق مرشحات المستأجر، وحدود التاريخ، ودفّق أو رقّم التصدير الكبير حيثما لزم، وتجنّب تحميل كل السجل التشغيلي في الذاكرة.

يجب أن تحافظ تغييرات الأداء على الصحة.

## المادة 25: تعريف الإنجاز (Definition of Done)

لا تكتمل الميزة المطلوبة إلا عند استيفاء كل البنود السارية:

- فُحص التنفيذ القائم.
- لم يُنشأ مجال مكرر.
- نموذج قاعدة البيانات والترحيل آمنان.
- حُفظت البيانات القائمة.
- فُرض عزل المستأجر.
- فُرض نطاق الفرع حيثما لزم.
- الـ API الحقيقي موجود.
- تحقق DTO مكتمل.
- الصلاحيات معرّفة ومُبذورة.
- الصلاحيات مفرضة في الـ backend.
- الصلاحيات مطبقة في الـ frontend.
- التدقيق مطبق.
- الـ frontend متصل بالـ API الحقيقي.
- الإنشاء يعمل.
- التفاصيل تعمل.
- التحرير يحدّث نفس السجل.
- إجراءات الحالة تعمل.
- حالات التحميل والفارغة والخطأ تعمل.
- الإدخال اليومي مقلل.
- البيانات القائمة تُعبأ تلقائياً بأمان.
- العربية مكتملة.
- الإنجليزية مكتملة.
- RTL يعمل.
- LTR يعمل.
- الاختبارات ذات معنى وتمر.
- سير العمل التشغيلي مثبت حيثما طُلب.
- لم تتغير ملفات غير مرتبطة.
- لم تُدخل بيانات مزيفة أو عناصر نائبة.
- حدّثت الوثائق فقط حيثما لزم.
- روجع الـ diff النهائي.
- أُبلغت الحالة النهائية بأمانة.

## المادة 27: تحميل القواعد الخاصة بالمهمة

لا تحمّل كل ملفات القواعد التفصيلية لكل مهمة. حمّل فقط الملفات ذات الصلة:

- تغييرات معمارية أو تنظيمية أو عبر الوحدات: `docs/agent-rules/architecture-and-tenancy.md`.
- Prisma أو SQL Server أو النماذج أو الفهارس أو الترحيحات: `docs/agent-rules/database-and-migrations.md`.
- NestJS أو API أو الصلاحيات أو التدقيق أو قواعد العمل: `docs/agent-rules/backend-and-security.md`.
- Next.js أو النماذج أو الجداول أو العربية/الإنجليزية أو F9 أو تجربة المستخدم: `docs/agent-rules/frontend-and-ux.md`.
- الاختبارات أو البناء أو إثبات المتصفح أو تحقق الإصدار: `docs/agent-rules/testing-and-proof.md`.
- تغييرات الصيانة: `docs/agent-rules/domain-rules/maintenance.md`.
- المخزون أو قطع الغيار: `docs/agent-rules/domain-rules/inventory.md`.
- الإنتاج: `docs/agent-rules/domain-rules/production.md`.

عندما لا يوجد ملف مُشار إليه: لا تخترع محتواه، واستمر بهذا الدستور، وأبلغ عن ملف القاعدة المفقود، ولا تنشئه ما لم تطلب المهمة صراحةً إنشاء ملفات قواعد.

عالج ملفات القواعد المُحمَّلة كإمتدادات إلزامية لهذا الدستور. عندما يتعارض برومبت خاص بمهمة مع هذا الملف، اتبع البرومبت الخاص بالمهمة فقط عندما يتجاوز صراحةً القاعدة ذات الصلة ولا يسبب فقدان بيانات أو فشل أمان أو سلوك قاعدة بيانات مدمراً.

## المادة 28: صناديق الحماية ومصفوفات النطاق

### 28.1 صناديق الحماية للنطاق (Scope Guardrails)

- صندوق الأمان (Security Box): لا تُقدم أبداً رمزاً يفتح فجوة أمان، حتى لو طُلب صراحةً (مثل كشف أسرار أو تعطيل مصادقة أو فرض خاطئ للمستأجر). عند وجود طلب خطير ارفضه وأبلغ عنه.
- صندوق البيانات (Data Box): لا تُنفذ أبداً أمراً قد يحذف أو يفسد أو يغيّر بيانات إنتاج حقيقية بطريقة غير قابلة للاسترداد دون اعتماد صريح وخطة تراجع موثقة.
- صندوق النطاق (Scope Box): التزم بالنطاق المعتمد. لا تتحول إلى مجالات غير معتمدة (مالية/مبيعات/مشتريات/رواتب) حتى لو طلبت ميزة ما ذلك ضمنياً.

### 28.2 مصفوفة النطاق الأساسية

|---|---|---|
| Auth / Users / Roles / Permissions | مطبق | توسيع فقط دون كسر |
| Companies / Branches / Administrations / Departments | مطبق | توسيع فقط دون كسر |
| Machines / Asset Register | مطبق | توسيع فقط دون كسر |
| Maintenance / CMMS | مطبق | توسيع فقط دون كسر |
| Inventory | مطبق | توسيع فقط دون كسر |

| Reports / Search / Audit / Notifications / Settings | مطبق | توسيع فقط دون كسر |
| Production | لم يبدأ | بناء شرائح رأسية تدريجياً بترتيب المادة 18 |
| Finance / Sales / Purchasing / HR / AI / IoT / BI | غير معتمد | لا تفتح إلا بموافقة صريحة |

## المادة 29: حقوق الكتابة والاستئذان قبل الالتزام

- للقراءة والتحليل والتخطيط: لا استئذان.
- لإنشاء/تعديل ملفات داخل المستودع مرتبطة بالمهمة: مسموح (أنت مطالب بها).
- للتغييرات المدمرة أو واسعة النطاق (ترحيلات تراجعية، حذف ملفات، إعادة هيكلة كبرى): استئذان مسبق.
- للالتزام والدفع: فقط عند طلب صريح من المستخدم، ثم راجع الـ status والـ diff أولاً.
- للتغييرات خارج النطاق الذي أقره المستخدم: لا تفعل دون سؤال.
